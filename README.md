# RTSEngine

RTSEngine — небольшой C++/SDL3 проект с изометрической картой, камерой, процедурной генерацией и отдельным игровым слоем.

Этот файл объединяет всю основную документацию проекта в одном месте: архитектуру, устройство модулей, правила оформления и план развития.

## Архитектура

```text
Game
   │
   ▼
Engine
   │
   ├── Core
   ├── Camera
   ├── Math
   ├── Render
   └── Modules
```

### Разделение ответственности

- Game — игровой слой, сущности и правила игры.
- Engine — базовая инфраструктура приложения.
- Core — конфигурация и время.
- Camera — управление видимой областью.
- Math — изометрические преобразования.
- Render — отрисовка кадра.
- Modules — прикладные подсистемы, включая TileMap.

### Поток данных

1. `main.cpp` создаёт мир и запускает рендер.
2. `Render()` инициализирует SDL и запускает цикл кадра.
3. `Time` обновляет delta time и FPS.
4. `Camera` смещает область просмотра.
5. `MapGenerator` наполняет карту данными.
6. `Isometric` переводит координаты мира в экранные.

### Диаграмма связей

```text
main.cpp -> Render -> Camera
                   -> Time
                   -> Map
                   -> Isometric
Map -> MapGenerator
Game -> Units
```

## Устройство движка

```text
Engine
   ├── Core
   ├── Camera
   ├── Math
   ├── Render
   └── Modules
```

### Core

- `EngineConfig.h` — общие константы проекта.
- `Time/EngineTime.*` — delta time, elapsed time и FPS.

### Camera

- `Camera.*` — позиция камеры, движение и ограничение по карте.

### Math

- `Isometric.*` — преобразование координат мира в экранные.
- `ScreenPoint.h` — вспомогательная точка для экранных координат.

### Render

- `SDLRender.*` — создание окна, рендерера и главный цикл вывода.

### Modules

- Подсистемы уровня движка, которые можно расширять отдельно от ядра.

### Граница ответственности

Движок отвечает за инфраструктуру. Игровые правила, сценарии и конкретные сущности остаются в `Game`.

## TileMap

```text
TileMap
   ├── Tile
   ├── Map
   └── MapGenerator
```

### Основные сущности

- `Tile` — описание типа поверхности и объекта на клетке.
- `Map` — размеры карты и линейный массив клеток.
- `MapGenerator` — генерация леса, озера и гор.

### Модель карты

```text
Map
 │
 ├── Ground
 ├── Objects
 └── Units
```

Карта в текущем виде хранится как плоский массив символов. Это делает структуру простой и удобной для ранней версии проекта.

### Генерация

- `CreateForest()` заполняет участок картой леса.
- `CreateLake()` формирует водную область.
- `CreateMountains()` задаёт горный участок.
- `GenerateMap()` объединяет все правила генерации.

### Что можно развивать дальше

- Слои карты.
- Разные типы поверхности и объектов.
- Разбиение на чанки.
- Отдельное хранение статической и динамической информации.

## Рендер

```text
Render()

↓

Update time

↓

Update camera

↓

RenderMap()

↓

DrawIsometricTile()

↓

SDL_RenderPresent()
```

### Роли функций

- `Render()` запускает SDL, создаёт окно и управляет игровым циклом.
- `RenderMap()` проходит по карте и готовит отрисовку каждой клетки.
- `DrawIsometricTile()` рисует ромб тайла по экранным координатам.

### Что важно помнить

- Рендер должен зависеть от данных карты и камеры, а не от внутренних деталей генерации.
- Цвет и форма тайла должны быть определены на одном уровне, чтобы не размазывать визуальные правила по всему коду.

### Следующий шаг развития

- Вынести отрисовку земли, объектов и юнитов в отдельные этапы.
- Добавить текстуры или атлас спрайтов.
- Разделить фон, мир и интерфейс.

## Математика

### Состав

- `Isometric.h` и `Isometric.cpp` — преобразования координат.
- `ScreenPoint.h` — экранная точка в вещественных координатах.

### Основные операции

- `WorldToScreen()` переводит координаты клетки в позицию на экране.
- `ScreenToWorld()` делает обратное преобразование.
- `GetMapPixelWidth()` оценивает ширину карты в пикселях.
- `GetMapPixelHeight()` оценивает высоту карты в пикселях.

### Смысл преобразований

Изометрия нужна для того, чтобы плоская карта выглядела как наклонённая сцена, но при этом оставалась простой в расчётах.

### Дальнейшее расширение

- Геометрия для коллизий.
- Поиск расстояний.
- Проверка видимости.
- Поддержка дополнительных проекций.

## Игровой слой

### Состав

- `Game/Units/Unit.h` и `Unit.cpp` — модель юнита и действия над ним.

### Роль игрового слоя

Игровой слой хранит сущности, правила взаимодействия и будущие игровые команды. Он использует инфраструктуру движка, но не должен зависеть от того, как именно устроен рендер.

### Что уже есть

- Создание юнита через ввод.
- Печать состояния юнита.
- Простая атака между юнитами.

### Что логично добавить дальше

- Очередь команд.
- Несколько типов юнитов.
- Фракции и принадлежность.
- Размещение на карте через отдельный слой логики.

### Связь с движком

Игровые сущности используют карту, камеру и рендер только через публичные интерфейсы движка.

## Правила оформления кода

### Именование

- Типы, структуры, классы и функции верхнего уровня оформляются в `PascalCase`.
- Переменные и параметры функций оформляются в `camelCase`.
- Константы обозначаются через `constexpr`, а не через `#define`.

### Организация файлов

- Один логический тип или модуль должен иметь свой заголовок и реализацию, если это оправдано.
- Заголовки должны включать только необходимые зависимости.
- Где возможно, лучше использовать предварительные объявления.

### Стиль кода

- Избегать `using namespace std`.
- Предпочитать простую и читаемую структуру функций.
- Не смешивать в одном файле отрисовку, вычисления и бизнес-логику без необходимости.
- Писать комментарии только там, где они помогают понять назначение модуля или сложную логику.

### Комментарии

- Шапка файла должна кратко объяснять назначение модуля.
- Комментарии внутри функций нужны только для нетривиальных участков.
- Не дублировать очевидный код комментариями.
